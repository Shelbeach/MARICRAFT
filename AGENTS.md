# MARICRAFT — правила для Codex

Этот файл действует для всего учебного Godot-проекта. Перед задачей прочитай:
1. docs/CURRENT_STATE.md — что реально сделано и какое задание разрешено сейчас.
2. GAME_DESIGN.md — правила игры: [У] утверждено, [Р] рабочая гипотеза, [О] открыто.
3. docs/DEVELOPMENT_PLAN.md — этапы и критерии приёмки.
4. docs/ARCHITECTURE.md — разделение ответственности и структура проекта.
5. docs/ART_DIRECTION.md — при задачах с изображениями и интерфейсом.

## 1. Безопасность проекта и дисков

- Проект MARICRAFT является **совершенно отдельным** от Not Another Night / ForestGame.
- Рабочий корень по умолчанию: D:\Projects\MARICRAFT\. Если каталог ещё не существует, при первом задании уточни/создай только его; не пытайся угадать другие диски.
- **Никаких изменений** в C:\GameProjects, проектах Not Another Night / ForestGame, связанном с ними Git на E: и других чужих каталогах.
- Все исходники, сцены, ассеты, документы, скриншоты, экспорт и рабочие файлы MARICRAFT размещать внутри корня на D:. Большие промежуточные файлы также направлять на D:, не заполнять C:.
- Уважать .gitignore; не коммитить .godot/, кэши, артефакты сборки, видео, огромные исходники и промежуточные эксперименты.
- **Не создавать Git-коммиты, автоматические снимки, ZIP-копии проекта и несколько полных резервных копий**, если не запрошено отдельно. Если нужно инициализировать Git, разместить .git только на D: и сначала убедиться в исключениях. Не очищать чужие файлы и не менять глобальные настройки Windows.
- Перед любым удалением, перезаписью принятого ассета или массовой реструктуризацией — проверить точные цели и получить разрешение владельца.

## 2. Технические ограничения

- Только Godot 4 Standard + GDScript; в Project Settings использовать рендер Compatibility.
- Цель — **работающая Web/HTML5-сборка в браузере на статическом HTTPS-хостинге**, без бэкенда. Это не побочный экспорт: проверяй совместимость с Web на протяжении разработки.
- На первом этапе узнать фактическую версию Godot, наличие export templates и путь его исполняемого файла; записать в docs/CURRENT_STATE.md. Не предполагать версию по старым документам.
- Для Web предпочесть экспорт без многопоточности. Прогресс — локально в браузере через user://; предусмотреть версию сохранения, повреждённый файл, недопущение повторной выдачи наград.
- Игровой код и UI должны работать с выбранным человеком и огром, а также со всеми тремя формами без копирования общей логики.
- Всё, что влияет на сердца, кошелёк, стоимость продолжения, очки, награды и открытие уровня, изменять через единый слой состояния игры; UI только отображает.

## 3. Объём каждой задачи и качество

- Выполняй **только текущий согласованный этап/промпт**. Не переходи самостоятельно к следующей локации, не подменяй серые блоки финальной графикой, если этап этого не требует.
- Предпочтительны большие, **законченные, проверяемые** задачи; самостоятельно доводи начатый этап до запуска и проверки, не останавливайся на первой синтаксической ошибке.
- Сохраняй архитектуру разделённой: общие правила кампании, персонаж, уровень, враги, объекты и UI не должны быть одним огромным скриптом.
- Используй повторно общие сцены/ресурсы. У каждого вознаграждаемого игрового объекта должен быть стабильный ID для защиты от повторных начислений.
- Утверждённые положения [У] не менять без разрешения. При пробеле [Р]/[О] выбери разумный обратимый вариант, запиши в docs/DECISIONS.md как «предложение»; крупный спорный выбор передай владельцу.
- Не исправляй несвязанные механики «заодно». Не называй временный прямоугольник или тестовый звук окончательным ассетом.

## 4. Серый прототип и графика

- Пока идёт этап серого прототипа, использовать различимые простые формы/цвета; **коллизии и масштабы уже должны соответствовать будущей игре**.
- Утверждено художественное направление №3: **2D мультяшный фэнтези-комикс**. Оно не означает разрешение использовать официальные знамёна, символику Альянса/Орды и копировать конкретные изображения Warcraft/Mario.
- Концепт в art_source/references/ — **только ориентир**, а не готовый тайлсет или фон. Отдельные спрайты, тайлы и слои параллакса должны создаваться изолированно и согласованно.
- Не внедряй сгенерированные ассеты в игру до проверки пропорций, альфа-канала, границ кадра, читабельности в целевом масштабе и утверждения владельцем, если требуется.

## 5. Дебаг, проверка и сдача результата

- Подготовить **отдельное русскоязычное меню разработчика (F1)**: бесконечные сердца, полёт, неуязвимость, переход между уровнями, изменение монет/формы, управление боссом, показ коллизий. Реализовать по мере появления соответствующих систем.
- Дебаг-команды должны быть отключены в финальной публичной Web-сборке. Не допускать сохранения читов в обычный игровой профиль.
- Перед отчётом выполнить доступные проверки: импорт сцен Godot без ошибок, запуск игры, целевые автоматические сценарии, при наличии export templates — браузерный smoke test.
- **Не выдавать кодовый обзор за игровой тест**. Если нет возможности запустить GUI или браузер, честно записать «не проверено», а не «успешно».
- Готовить понятную демонстрацию: краткий отчёт, при необходимости скриншоты реальной сцены и короткое видео/HTML-обзор. Временные крупные файлы сохранять на D:, не включать в Git.
- Каждый этап завершать обновлением: docs/CURRENT_STATE.md, docs/REPORT_IMPLEMENTATION_TESTS.md, docs/REPORT_UI_ASSETS.md (если затронут UI/арт), docs/DECISIONS.md (если принимались решения), и при изменении игровых правил — GAME_DESIGN.md.

## 6. Стандарт финального ответа Codex после этапа

Отвечай кратко на русском:
1. **Сделано:** реальные функции и пути основных изменённых файлов.
2. **Проверено:** конкретные команды/сценарии и результат; ручное отдельно от автоматического.
3. **Посмотреть:** как запустить и проверить, ссылка/путь к отчёту или демонстрации.
4. **Осталось:** реальные недочёты/ограничения, следующий этап (не начинать без согласования).

Нельзя выдумывать результаты тестов, скриншоты, выполненные функции или участие других студентов.
